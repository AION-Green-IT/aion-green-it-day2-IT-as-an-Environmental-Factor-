========================================================================
AION MODULE PLAYGROUND — MASTER BUILD PROMPT & STANDARD
Version 1.0 · derived from Module 1 (Green IT), Day 1, built and shipped
========================================================================

This file is the reusable standard for every AION training-day playground
after Day 1. Day 1 was built, corrected through many rounds of real
feedback, and shipped. Everything that survived that process is written
down here. Everything that failed is written down in PART 15, which is
the most valuable part of this file.

The subject matter is a variable. The architecture, the rules, the
component contracts, the visual standard and the learning model are not.

------------------------------------------------------------------------
PART 0 — HOW TO USE THIS FILE
------------------------------------------------------------------------

You (the human) do two things:

  1. Fill in PART 16 (CURRICULUM INTAKE) with the new day's material.
  2. Hand the assistant this entire file, with PART 16 filled in.

The assistant then builds the whole playground from PART 1 to PART 14
without asking which framework, which colours, which routes or which
interaction patterns to use. Those are settled here.

Rules of engagement for the assistant:

  - Read this file end to end BEFORE writing any code.
  - Where PART 16 is silent, follow the Day 1 default described here.
  - Where PART 16 contradicts this file, PART 16 wins for CONTENT, and
    this file wins for STRUCTURE, RULES and VISUAL STANDARD.
  - Do not ask permission to follow this file. Ask only when PART 16 is
    ambiguous about content in a way that changes what gets built.
  - Scaffold empty-but-correct routes first, then fill them one at a
    time. Do not attempt the whole build in one pass.
  - Verify in a real browser before reporting anything as done.

A note on scope: Day 1 shipped 11,887 lines of TypeScript across 79
files in app/, components/, data/ and lib/. Plan for that size.

------------------------------------------------------------------------
PART 1 — WHAT YOU ARE BUILDING (shape, independent of subject)
------------------------------------------------------------------------

A static, single-language, offline-capable web playground that supports
one training day. It is NOT a course platform, NOT a quiz engine, and
NOT a certificate mill. It is an OBSERVATION AND DECISION SURFACE that a
mentor uses in a room with participants, and that participants use alone
alongside a paper worksheet.

The playground has five kinds of surface:

  TAB 1  LEARN            — teaches the concepts. Verdicts allowed.
  TAB 2  TRAINING GROUND  — gamified practice. Verdicts allowed.
  TAB 3  CASE A (L1)      — observation only. Verdicts forbidden.
  TAB 4  CASE B (L2)      — observation + one committed decision.
  TAB 5  CASE C (L3)      — observation + allocation under shortfall.
  TAB 6  TASK MAP         — which task uses which case and which widget.

The three case tabs are GRADED SURFACES. The worksheet's answer key
points at them. That is why they never reveal answers.

The separation is absolute and is the single most important structural
rule in this file:

  LEARN and TRAINING teach with GENERIC, INVENTED examples.
  CASES carry the assessed material and never teach.

If a case company's content appears in LEARN, the assessment is broken.

------------------------------------------------------------------------
PART 2 — NON-NEGOTIABLES (violate any of these and the build fails)
------------------------------------------------------------------------

N1. VERBATIM CONTENT.
    Every fact, label, chip, role name, initiative name and stakeholder
    name that comes from the curriculum ships EXACTLY as written in
    PART 16. Do not paraphrase, do not "clean up", do not translate,
    do not improve the grammar. Worksheets and answer keys reference
    exact on-screen strings. Rewording a string silently breaks a
    printed answer key that is already in a room.

N2. REVEAL RULES.
    - LEARN: reveals ON. Widgets teach; show verdicts freely.
    - TRAINING GROUND: reveals ON. Gamified practice with reveal cards.
    - CASE TABS: reveals OFF. Never label a finding as "flaw",
      "problem", "issue" or "correct category". Category chips render
      as "Topic area: X" and are neutral tags, not verdicts.
    - EXCEPTION, added after Day 1 feedback: a case tab MAY carry a
      decision surface with an answer key, PROVIDED the key is gated
      behind the learner's own committed choice, and the learner sees
      the trade-off of their own choice first. See PART 7.

N3. NO CONTENT LEAKAGE.
    LEARN and TRAINING never use content, names or numbers from the
    graded case companies. They use generic or invented companies.
    Leaking assessment answers into the teach surface is a hard fail.

N4. FIXED CATEGORY SET.
    The curriculum's topic categories are fixed at intake and used
    everywhere with exactly the labels and short codes given in
    PART 16. Do not invent an extra category. Do not substitute a
    general UX or accessibility framework (POUR, heuristics, etc.)
    for the curriculum's own categories.
    Day 1 used five: Energy (E), Resources (R), Emissions (Em),
    Use (U), Organisation & Governance (G).

N5. EVERY ANSWER IS FINDABLE IN THE APP.
    Every hotspot, tile, card, condition and stakeholder has a stable,
    human-readable, lowercase-kebab-case id that a worksheet FIND IT
    line can point at. Ids are a contract and survive deploys. If a
    build decision forces a rename, list every renamed id in README.md
    under "ID changes".

N6. NO EXTERNAL RUNTIME DEPENDENCIES.
    No backend calls. No third-party analytics. No external image CDNs.
    No icon fonts. No emoji in the DOM of case or scenario surfaces.
    Illustrations are inline SVG built in-repo, or a raster hero stored
    in /public/assets. Fonts are a self-hosted or system fallback stack.
    State lives in localStorage only.

N7. PRE-METRIC (carry forward unless PART 16 overrides).
    Day 1 forbade absolute figures — no CO2 estimates, no kWh, no
    currency. Simulators used ratios, indices and abstract points.
    Keep this default: a training day about judgement should not hand
    out numbers that look authoritative and are invented. If the new
    curriculum genuinely supplies real figures with sources, PART 16
    must say so explicitly and cite them.

N8. NO SCORE SCREEN.
    No pass/fail, no certificate, no percentage at the end. XP and
    badges exist only in TRAINING GROUND and measure ground covered,
    never quality of judgement. Case tabs and scenarios award nothing.

PART 3 — TECH STACK AND PROJECT LAYOUT (exact)
------------------------------------------------------------------------

STACK — do not substitute:

  Next.js 14 (App Router)     next@14.2.5
  React 18                    react@18.3.1  react-dom@18.3.1
  TypeScript 5, strict        typescript@5.5.3
  Tailwind CSS 3              tailwindcss@3.4.6
  Zustand 4 + persist         zustand@4.5.4
  clsx                        clsx@2.1.1

  Node >= 18.17.0 (REQUIRED — Next 14 refuses to build on Node 16)

  NO component library. No shadcn/ui, no MUI, no Chakra. The design
  system here is small enough to build from Tailwind primitives, and a
  library would drag in styling that fights the brand tokens.

  NO animation library. Tailwind transitions plus `motion-safe:` cover
  everything Day 1 needed.

STATIC EXPORT — this is what makes deploys stop failing:

  next.config.mjs:
    const nextConfig = {
      reactStrictMode: true,
      output: "export",
      images: { unoptimized: true },
      trailingSlash: true,
    };

  Consequences you must design around:
    - No server-side redirects. The root route redirects on the client
      and MUST also render a real <Link> fallback for no-JS and for
      crawlers.
    - No route handlers, no server actions, no middleware.
    - next/image works but does not optimise; size your rasters by hand.

THE HARD RULE ON CONTENT PLACEMENT:
  Content lives in data/*.ts. Components contain layout and behaviour.
  If you find yourself typing a sentence of curriculum into a .tsx file,
  stop and move it to data/. This is what makes the verbatim rule (N1)
  auditable — a reviewer can diff data/ against the curriculum.

PART 5 — GLOBAL STATE AND PROGRESS
------------------------------------------------------------------------

Zustand with the persist middleware, one localStorage key per module,
e.g. "aion-<module-slug>".

  Progress (persisted):
    xp: number
    streak: number
    badges: string[]
    visited: { hotspots: string[]; learnWidgets: string[];
               trainingCards: string[] }
    training: { seenCardIds: string[];
                correctByCategory: Record<CategoryCode, number> }
    scenario: { <scenarioKey>: <ScenarioState> }     // if the day has one

  Session (NOT persisted):
    resetCount: number

THE RESET PATTERN — Day 1 got this wrong first, so copy it exactly.

  Clearing the store is not enough. Component-local state (an open
  widget, a round's answers, a card counter) survives a store reset and
  the user sees "CARDS SEEN 1/15" after a reset that claimed to clear
  everything. Fix:

    reset: () => set((s) => ({ ...emptyProgress,
                               resetCount: s.resetCount + 1 })),

  and a boundary that keys page content on it:

    // components/chrome/ResetBoundary.tsx
    const resetCount = useProgress((s) => s.resetCount);
    return <div key={resetCount} className="contents">{children}</div>;

  resetCount is deliberately excluded from `partialize`: it is a signal
  within one session, not progress.

  Reset must be CONFIRMED (a ConfirmDialog naming exactly what will be
  lost) and must NOTIFY on completion. A destructive control that fires
  on one click is a bug report waiting to happen.

COMPLETION TRACKING — lib/completion.ts

  ONE function answers "what is still open" for the whole app, and every
  surface that asks the question calls it. It returns groups:

    { id, label, href, unit, items: [{id, label, done}], done, total }

  Groups on Day 1: learn widgets, scenario decisions, training cards,
  badges, and one group per case board's findings.

  The <OpenItems> component renders a group, filtered by `only={[...]}`,
  and is placed on the tab it describes as well as on the Task Map.

  RULE LEARNED THE HARD WAY: a completion hint must name the specific
  thing that is missing, with a link. "Something on this tab is still
  open" is worse than useless — the participant starts hunting instead
  of learning. Say: "3. Procurement without green criteria — not yet
  opened", and make it clickable.

PART 6 — THE SIX SURFACES IN DETAIL
------------------------------------------------------------------------

TAB 1 — LEARN

  Purpose: teach every concept the three cases will assess, using
  generic examples only (N3).

  Structure: an <Accordion> of levels (L1 Knowledge, L2 Application,
  L3 Management decision). Each level holds widgets. Accordion items
  are addressable by URL hash so a worksheet FIND IT line can deep-link:

    useEffect(() => {
      const fromHash = () => {
        const id = window.location.hash.replace("#", "");
        if (!id || !items.some((i) => i.id === id)) return;
        setOpen(id);
        requestAnimationFrame(() =>
          document.getElementById(id)?.scrollIntoView({ block: "start" }));
      };
      fromHash();
      window.addEventListener("hashchange", fromHash);
      return () => window.removeEventListener("hashchange", fromHash);
    }, [items]);

  Every widget is wrapped in <WidgetShell> which supplies: a numbered
  title, a one-line "what this is for", the widget body, and a
  "what this shows" readout. Widgets register themselves as visited.

  A widget must DO something. A widget that only displays text is a
  paragraph wearing a costume — delete it or make it interactive.

  Day 1 widget inventory (as a shape to imitate, not to copy):
    W1  side-by-side comparator with a live readout
    W2  flip cards (term -> plain-language definition)
    W3  category sorter with keyboard fallback (focus + press 1..5)
    W4  trade-off dials, committed with a button (see PART 15 #7)
    W5  impact/feasibility matrix, draggable
    W6  decision under incomplete information
    W7  governance org chart builder
    W8  12-month roadmap with trade-off feedback and an answer key
    W9  symbolic vs strategic sorter
    W10 service-life simulator (index, not absolute figures)
    W11 efficiency-ratio simulator (index, not absolute figures)

  Every widget that touches a quantity gets a SIMULATOR, not a
  paragraph. This was explicit Day 1 feedback: where the curriculum
  discusses a footprint, the learner moves a slider and watches an
  index move. Keep it pre-metric (N7).

  JARGON: every domain term is wrapped in <GlossaryText> which
  underlines it and opens a plain-language definition inline, and the
  full <GlossaryReference> sits at the bottom of the tab. Day 1
  feedback was blunt about this — an audience reading a second language
  cannot be handed "HVAC" and left there.

TAB 2 — TRAINING GROUND

  Purpose: fast, gamified practice on generic situations.

  Shape: N situations (Day 1: 15), one at a time. Read the situation,
  choose the category, the card flips and explains: what it is, who it
  affects, the fix, and the rule to take away.

  Scoring must be EXPLAINED BEFORE IT IS USED. Day 1 feedback: "if you
  want gamification, first say what it is for". So the tab opens with:
    XP      — points per match. Measures ground covered, nothing else.
    Streak  — matches in a row. Resets on a miss. No penalty.
    Badges  — one per category, lights when all its cards are matched.

  Being wrong must cost nothing and must be worth more than being
  right: the explanation is the product.

  A badge that will not light must SAY WHICH CATEGORY IT IS WAITING FOR
  and link to it. See the completion rule in PART 5.

TABS 3-5 — THE CASE BOARDS

  See PART 8. These are the assessed surfaces.

TAB 6 — TASK MAP

  A table: Task -> Level -> Case -> which LEARN widgets support it.
  Plus the full <OpenItems> across every group. This is the mentor's
  view and the participant's "am I done" view.

PART 7 — THE L1/L2/L3 LEARNING MODEL
------------------------------------------------------------------------

One integrated task per training day, revisited three times, getting
harder in ONE DIRECTION ONLY: less certainty, not more content.

  L1 — KNOWLEDGE            marking: OBJECTIVE
       Report what the instrument shows. No opinion required and none
       accepted. If two learners disagree, one has misread the widget.
       Case surface: pure observation. Hotspot board, nothing else.

  L2 — APPLICATION          marking: OBJECTIVE + JUDGED
       Choose between options whose consequences the learner can see.
       No single correct choice, but a correct set of facts underneath
       it. A defensible choice on wrong facts scores badly; so does a
       correct reading followed by reasoning that ignores it.
       Case surface: board + ONE committed decision with trade-off
       feedback, then an answer key if the curriculum has one.

  L3 — MANAGEMENT DECISION  marking: CONSTRAINT CHECK + RUBRIC
       Allocate resources that are deliberately insufficient. Defend a
       decision that cannot be fully evidenced. Only the constraint and
       the derived values are checkable; the rest is judged on whether
       the decision holds together under questioning.
       Case surface: board + allocation under a hard ceiling + a
       "what you postponed" field.

THE SENTENCE THE WHOLE FORMAT EXISTS TO TEACH:

  "A learner who finishes Level 3 without having given anything up has
   not finished Level 3."

DESIGN CONSEQUENCES:

  - THE SHORTFALL IS THE EXERCISE. At L3 the capacity must not cover
    the requirement. Day 1 used 6 measures costing 16 points against a
    capacity of 10. SAY SO ON SCREEN so nobody reports it as a bug.

  - BUILD IN ONE TRAP THE APP ITSELF REVEALS. A finding with no clean
    category, a meter with a structural ceiling, an option that looks
    free and is not. The app's own feedback teaches; the worksheet only
    records it.

  - ANSWER KEYS ARE GATED AND HONEST. If the curriculum supplies a key:
      1. The learner picks and COMMITS.
      2. The app shows the trade-off of THEIR choice first — what it
         buys and what it costs.
      3. Only then does "Show the answer key" appear.
      4. The key states plainly that the options it did not name are
         not wrong, and names what they are genuinely better at.
    Day 1 feedback drove this: "even the best option still has a
    downside, right?" Yes — and the key must say so, or it reads as a
    verdict and the learner stops thinking.

  - L3 GETS NO ANSWER KEY, EVER, unless the curriculum supplies one.
    Day 1's L3 case deliberately had none. Instead the app reports
    CONSEQUENCES: for each unfunded measure, what it leaves open,
    written without scolding.

  - EVERY L3 SURFACE ENDS WITH "the measure you consciously postponed",
    a free-text field, with the note that a blank answer has not
    finished the task. It is the field people leave empty and the one
    the group debrief turns on.

TONE FOR ALL FEEDBACK TEXT:
  Second person, declarative. No encouragement, no exclamation marks,
  no praise. State consequence, not correctness.
  Good: "You just chose a narrative. The instrument did not."
  Bad:  "Great job! That's the right idea!"

PART 8 — CASE BOARDS (the hotspot pattern)
------------------------------------------------------------------------

Every case tab is an ILLUSTRATION THAT CARRIES THE CASE. Not an
illustration next to the case. The picture is the interface.

Day 1 feedback that produced this rule: "the image is only decoration —
an image is supposed to help understanding". If a learner could delete
the picture and lose nothing, the picture has failed.

THE DATA CONTRACT (data/case-shared.ts — copy this file forward):

  export type HeroImage = {
    src: string; width: number; height: number; alt: string;
  };

  export type Zone = {                    // a clickable rectangle
    id: string; label: string;
    x: number; y: number; w: number; h: number;   // % of image box
  };

  export type Hotspot = {                 // one passage of the case
    id: string;
    label: string;
    x: number; y: number;                 // focus point for the zoom, %
    panel?: { x: number; y: number; w: number; h: number };
    categories: CategoryCode[];
    fact: string;                         // VERBATIM from curriculum
    onTheImage: string;                   // neutral description of what
                                          // is drawn there
  };

  export type ContextTile = { id: string; text: string };
  export type CaseBrief = { name: string; lines: string[] };

TWO MARKER SHAPES, ONE MEANING:

  - No `panel`  -> a round numbered POINT MARKER sits at (x,y).
    Use for continuous artwork (an isometric cutaway, a scene).
  - With `panel` -> the whole RECTANGLE is the click target, with the
    round number in its corner. Use for artwork drawn as titled panels.

  Both render as the same visual object so the learner learns one
  affordance. Never put a point marker in the middle of a comic panel:
  it covers the art and the target is smaller than the thing it names.

BEHAVIOUR (components/case/HotspotHero.tsx + CaseBoard.tsx):

  - Click a finding -> the board ZOOMS to it and a DETAIL CARD opens
    with: number, label, the verbatim fact, "On the illustration: ..."
    and the neutral topic chips.
  - Zoom is a CSS transform on a container, with the translate CLAMPED
    so no blank edge is ever exposed:

      const tx = clamp((FOCUS_X - (s * focus.x)/100) * 100, (1-s)*100, 0);

  - Markers COUNTER-SCALE (`scale(1/s)`) so they keep their size while
    the art grows.
  - Panels zoom LESS than points (Day 1: 1.9 vs 2.4). A panel is already
    a readable unit; zooming it as hard as a point pushes its own edges
    out of frame.
  - A "Zoom out" button appears while zoomed.
  - Esc clears the selection.
  - The company block is a separate zone with an "i" badge, opening the
    brief and the context tiles. It is never a finding.
  - Visited markers change fill (paper -> navy) so progress is visible
    on the artwork itself.

THE CATEGORY LEGEND — two cases:

  a) The artwork has the category arrows DRAWN INTO IT (Day 1 Case A).
     Overlay square-badged zones on them.
  b) The artwork does not (Day 1 Cases B and C).
     Render an HTML filter strip UNDER the board instead. Do not fake
     drawn arrows.

  Either way, selecting a category RINGS every marker carrying that tag
  (a coloured box-shadow) and lists them as clickable links in the card.
  Show the COUNT per category on the chip. The counts teach: Day 1's
  Case C reading "Organisation & Governance 7 of 10" tells the learner
  what kind of case it is before they open anything.

MANDATORY ON EVERY CASE TAB:

  - "Show all findings as list" toggle (R6). Same ids, same facts, same
    chips, same order, without the image. This is the screen-reader
    path and the mentor's projection path.
  - A count: "N of M findings opened".
  - An <OpenItems only={[caseKey]}> block naming what has not been
    opened yet.
  - A legend explaining the two badge shapes.

RASTER HEROES:

  - Store in /public/assets/<case>-hero.jpeg. Filenames are lowercase
    kebab-case with NO SPACES (a space in a filename becomes a URL
    encoding problem).
  - Target 2048px wide, quality ~82, under 1 MB. Day 1 received 3.6 MB
    and 3.8 MB files and compressed them by 75% with no visible loss:
      sips --resampleWidth 2048 --setProperty formatOptions 82 in.jpeg \
           --out in.jpeg
  - Keep all case heroes at the SAME ASPECT RATIO so the boards are the
    same shape. Day 1 settled on 2048 x 1117.
  - HERO_IMAGE.width/height must match the real file.
  - alt text describes the whole scene in one long sentence, left to
    right, naming every element a marker points at.

MEASURING HOTSPOT COORDINATES:
  Open the delivered image, read positions off it, convert to percent
  of width/height. Do NOT assume the generator produced the layout you
  asked for. Day 1 measured every marker against the real file.

------------------------------------------------------------------------
PART 9 — THE SVG STANDARD (visuals everywhere)
------------------------------------------------------------------------

RULE: every concept that can be drawn IS drawn, in inline SVG, in-repo.
A screen of continuous prose is a defect. Day 1's harshest feedback was
about exactly this ("that much text — look at our standard").

WHAT COUNTS AS A GOOD DIAGRAM:

  It shows a MECHANISM, not a mood. Ask: "after looking at this, can the
  learner predict something they could not predict before?" If not, it
  is decoration; delete it or redraw it.

  A diagram must NOT plot, rank or score the learner's options. On case
  surfaces that would be a verdict (N2). Draw the SHAPE OF THE
  TRADE-OFF, not the winner. Day 1 examples that pass:
    - a 12-week bracket bar showing how little runway exists
    - an impact/feasibility/visibility triangle labelled
      "reach two, lose one"
    - an evidence-vs-claim gap with the gap itself labelled "exposure"
    - a one-owner <-> shared axis with expertise and authority marked

INTERACTIVE BEATS STATIC:
  Where the learner has options, the DRAWING should respond to them.
  Day 1 feedback: "the options should show their result — look at case
  A". So a choice widget re-renders the diagram rather than printing a
  sentence under it.

TECHNICAL RULES:

  - Inline SVG in a .tsx component. No sprite sheets, no icon fonts,
    no external files, no emoji as iconography.
  - role="img" plus aria-labelledby pointing at a <title> and, where
    the drawing is complex, a <desc>.
  - Give the viewBox ROOM FOR LABELS OUTSIDE THE SHAPE. Day 1 clipped a
    triangle's labels and had to widen 320x120 to 320x150 and move the
    notes outside the geometry.
  - Colours come from the brand tokens and the category tokens. Never a
    hardcoded hex that is not in PART 4.
  - Stroke widths 1.5-2 at the drawing's natural scale; thin strokes
    disappear when the board is zoomed out on a laptop.
  - All motion behind `motion-safe:`. Respect prefers-reduced-motion.
  - Text inside SVG is a last resort: it does not reflow and it cannot
    be translated. Prefer HTML labels positioned over the SVG.
  - Every SVG must be legible at 320px wide. Test it.

WHERE SVG IS MANDATORY:
  - Every LEARN widget's illustration and readout.
  - Every scenario phase briefing (Day 1: 4 briefing diagrams).
  - Every category diagram and org chart.
  - Every meter, gauge, bar and index readout.
  - Stakeholder avatars and any repeated glyph set.
  - Endings / debrief illustrations.

WHERE A RASTER IS ALLOWED:
  Only the case hero, and only because a rich scene with people, depth
  and texture is beyond hand-written SVG. Everything else is SVG.

PART 10 — IMAGE PROMPTS (ready to paste into an image generator)
------------------------------------------------------------------------

CONTEXT FOR WHOEVER USES THESE:
  These produce the case hero only (PART 8). The generator is external —
  the assistant cannot generate images. Generate, save into

--- HOW TO FILL EITHER TEMPLATE ---

  1. List the case's findings from the curriculum. Aim for 8-10.
  2. Give each finding a PHYSICAL MANIFESTATION — a thing that can be
     drawn, not a concept. "No sustainability criteria in procurement"
     becomes "a printed form with three columns, the first two ticked
     and the third completely blank".
  3. An ABSENCE is drawn as an EMPTY CONTAINER: a blank dashboard, an
     org chart with one empty box, a column with nothing in it. This is
     the single most useful trick in this file — it makes a governance
     gap visible, and governance gaps are most of what these cases are.
  4. If a finding is about something happening in more than one place
     (decentralisation, inconsistency), draw it TWICE, differently. One
     team unpacking laptops reads as normal; two teams unpacking
     different boxes in the same building is the finding.
  5. Put the findings that carry the answer key in separate panels so
     they can be discussed one at a time.

--- AFTER GENERATING ---
  1. Save as /public/assets/<case>-hero.jpeg — lowercase, no spaces
     (rename if the generator added the case title as the filename).
  2. Compress to ~2048px wide, under ~1 MB (see PART 8). Day 2 shipped
     ~2 MB files; smaller is better for the deploy.
  3. Point `HERO_IMAGE.src` at the .jpeg with matching width/height, and
     keep `schematic` on the SVG so the toggle stays.
  4. Have the assistant MEASURE each white placeholder circle off the real
     file and set `imgX`/`imgY` (+`imgPanel` for panels) and the zone
     `imgX/imgY/imgW/imgH`. Leave `x`/`y` (the SVG coordinates) untouched.
     Rewrite each `onTheImage` line from what the picture actually shows.
  5. If a panel came back merged, missing or garbled, REGENERATE. A marker

PART 11 — INTERACTION AND COPY RULES (re-read after coding)
------------------------------------------------------------------------

R1. On case tabs the words "problem", "flaw", "issue", "correct",
    "wrong", "improvement", "should" MUST NOT appear. Neutral words:
    "fact", "finding", "observation", "topic area", "condition",
    "role", "interest", "constraint".

R2. On case tabs never show which category is the "right" answer. A
    chip is a topic tag. Two chips on one finding are shown without
    ranking.

R3. In LEARN and TRAINING, verdicts and answers are expected. Use the
    answer variant of the category chip there.

R4. Every clickable surface has a visible 2px purple focus ring, an
    accessible name matching its on-screen label, and a hover state
    that does not rely on colour alone.

R5. Every modal is dismissable by Esc, backdrop click and a visible
    Close button. Focus is trapped while open and restored on close.

R6. Every case tab has a "Show all findings as list" toggle rendering
    the same ids, facts and chips in the same order, without the image.

R7. Nothing on a case tab suggests an action. Case tabs are observation
    surfaces. The decision surfaces below them are separate, labelled,
    and belong to the task.

R8. No tooltips that reveal category answers on hover.

R9. TWO-STEP COMMIT ON EVERY CHOICE THAT ADVANCES STATE.
    Selecting must not advance. The learner selects, sees what they
    selected, and presses a separate confirm control. Day 1 feedback:
    "when you have to choose, don't jump straight to the next thing —
    let them change their answer before they are sure."
    Before the confirm, show what IS knowable: budget arithmetic, who
    has a stake. Do NOT preview what is not knowable — how people will
    react — and say so on screen: "How they react is not knowable yet."

R10. NO DEFAULT THAT COUNTS AS AN ANSWER.
    A dial resting at its midpoint is not a decision. If the midpoint
    is a legitimate answer, the learner must be able to choose it
    explicitly — which means a commit button, not "all sliders moved".

R11. FOLD LONG TEXT.
    Any block over roughly 120 words is collapsed behind a
    <Collapsible> with a meaningful summary line, or split into an
    inbox / accordion / stepper. Settled steps collapse to
    "You chose: <title>". Never ship a wall of prose.

R12. NAME THE THING THAT IS MISSING.
    Every progress hint says exactly which item is open and links to
    it. Never "something on this tab".

R13. EXPLAIN BEFORE YOU SCORE.
    Any scoring, badge or meter is preceded by a short block saying
    what it measures and what it does not.

R14. EVERY DOMAIN TERM IS GLOSSED inline on first use, and again in a
    glossary at the foot of the tab.

R15. WRITE FOR THE PARTICIPANT, NOT THE MENTOR (Day 2 feedback).
    This site is used by participants for self-study, so the voice is
    theirs. Address the learner as "you". No "the room", "the mentor",
    "ask the room", "run one level per block". Day 1 wrote LEARN copy as
    a mentor's script; rewrite it as something a person reads alone and
    understands without a facilitator. A single quiet "Tip:" for the
    solo learner is fine; a "For the mentor:" block is not.

R16. EVERY MATERIAL OPENS WITH "WHAT'S IN IT FOR YOU".
    Before the activity, one short line in the learner's voice: why this
    is worth their time and what they will be able to do afterwards —
    concrete, tied to a situation they will actually face ("next time
    someone says 'replace the laptops early to save power', you'll be
    able to check whether it helps"). It is a benefit, not a summary.
    In LEARN this is the WidgetShell "What's in it for you" slot (the
    `why` field); give cases and scenarios the same one-line opener.

R17. VISUALISE HOW CONCEPTS RELATE, NOT JUST WHAT THEY ARE.
    When a topic is a set of related ideas (e.g. direct vs indirect
    energy vs resources vs sufficiency), lead with ONE inline-SVG picture
    that shows how they connect around a concrete object — a device with
    the plug as direct energy, the factory/lorry and cloud as indirect,
    the parts inside as resources — before the definitions. A learner
    grasps a relationship from a diagram far faster than from four
    paragraphs. Follow the SVG standard in PART 9 (real <desc>, brand
    tokens, no baked text that needs translating). See
    components/learn/EnergyResourceDiagram.tsx and CategoryDiagram.tsx.

R18. MAKE THE CONCEPT DIAGRAM INTERACTIVE (click a part -> zoom + read).
    A relationship diagram is not a static picture. Each part is a
    focusable button (role="button", tabIndex, Enter/Space); selecting it
    zooms the SVG into that part (transform on a wrapping <g> with a
    transition), dims the others, and shows that part's explanation next
    to it, with a "Zoom out" control. Wire selection to the same state the
    text cards use, so the diagram and the cards drive one explanation.
    See EnergyResourceDiagram.tsx (the four energy/resource concepts) and
    GovernanceChart.tsx (the five roles) — the same pattern as the case
    hero: a picture you click beats a picture you look at.

R19. NO EXPLANATION IS TEXT-ONLY — GIVE IT A SUPPORTING VISUAL.
    Wherever an explanation is more than a couple of lines, add a small
    visual beside it, matched to its shape:
      - a set of items -> an icon per item (W2 energy consumers);
      - a rising scale -> a ladder (W9 symbolic -> operational -> strategic);
      - options vs criteria -> a colour heat grid (Task 2 A/B/C);
      - a sequence over time -> a horizon bar (short -> medium -> structural);
      - a change -> a Before -> After block with state icons (Training cards).
    Inline SVG or simple flex/Tailwind blocks, brand tokens, no baked text.
    The verdict colours, chips and meters already carry meaning; lean on
    them. A wall of prose is the failure mode this rule exists to prevent.

PART 12 — ACCESSIBILITY MINIMUMS
------------------------------------------------------------------------

- Body text >= 4.5:1 against paper; chip text >= 4.5:1 against its chip.
- Full keyboard operability. Drag-and-drop widgets need a keyboard
  fallback (focus an item, press 1..N to assign it to a bucket).
- prefers-reduced-motion disables zoom transitions and any pulse.
  Use Tailwind `motion-safe:` prefixes rather than a media query in JS.
- Every SVG illustration: role="img" + aria-labelledby -> <title>.
- Every hotspot button: aria-pressed, plus an sr-only label that also
  announces "(opened)" once visited.
- The detail card is aria-live="polite".
- <html lang> is set to the module language.
- Hit targets >= 28px on phones. Markers counter-scale but must not
  shrink below that.
